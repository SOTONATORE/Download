## 2. Ключ конфигурации

- Ключ: `verified`, тип: логическое значение, **умолчание: `true`**.
- Комментарий в `config.default.yaml`:

```yaml
# Только проверенные хосты: true оставляет предложения Vast с verification=verified и отбрасывает
# deverified; false поиск по этому полю не ограничивает. Смысл значений взят из пробы 13.10.2026
# (2 из 6 предложений verified), но не сверен с веб-интерфейсом Vast: UNVERIFIED.
verified: true
```

- Загрузка: как у `interruptible`, те же проверки типа. Строка вместо `true`/`false` и `null` дают ошибку конфигурации (код выхода 2).
- Отсутствующий ключ читается как `true` (правило 8, fail closed). Это исключение из общего правила «все ключи обязательны», поэтому комментарий в заголовке файла уточнён. Если нужен строгий режим (отсутствие = ошибка до любых трат), это одна правка в `config_loader.py`.

## 3. Новая строка лога неудачного старта

Формат строки не менялся, снята только обрезка. Пример получен из нового теста (`test_status_message_over_200_chars_is_logged_in_full_and_redacted`) на искусственном тексте; повтор «длинный текст» сокращён (в тесте он повторён 40 раз):

- Строка одна: переводы строк превращаются в пробелы.

- До изменения текст обрывался на 200-м символе и заканчивался `…`. Всё, что шло дальше, включая причину в конце статуса (например, `unresolvable CDI devices` из реального сбоя), в лог не попадало.

## 4. Что остаётся UNVERIFIED

1. **Смысл `verification` в веб-интерфейсе Vast.** Значения `verified` и `deverified` зафиксированы в ответе API (проба 13.10.2026). Соответствие веб-метке «Verified» или «Unverified» не проверено. Поле `is_vm_deverified` не используется.
2. **Причина сбоев.** Карты 58482, 38389, 36773 и скриншот с хостом 362355 (Unverified) в переданных логах отсутствуют: лог содержит только пробу. Совпадение `53395400` (deverified в пробе) с одним из сбоев не доказывает связь: это один случай.
3. **Переменная `-p 8000:8000`.** Не менялась и не проверялась. Это отдельная гипотеза, и она не подтверждена этим изменением.
4. **Серверный фильтр.** Фильтр работает на стороне Vast. Клиент не проверяет поле `verification` в ответе. Проба показала, что серверный параметр действует (2 из 2 результатов verified), но это проверено один раз.

## 7. Риски

1. **Пул может быть пустым или очень маленьким.** В пробе без фильтра 2 из 6 предложений проверены. С фильтром пришли 2, но одно из них по значениям пробы отбрасывается ценой трафика (40 USD за ТБ при пороге 4.1). Остаётся одно предложение. Пустой пул даёт существующее поведение: предупреждение «Подходящих предложений Vast нет, повтор позже», повтор поиска до срока `job_deadline_min` или бюджета. Непроверенный хост при этом не арендуется. Запуск может завершиться частично.
2. **Если проверенные хосты падают с той же ошибкой**, например `unresolvable CDI devices`, причина не в `verified`. Следующая гипотеза — переменная `-p 8000:8000` (сейчас не менялась).
3. **Защита только серверная.** Если API перестанет учитывать `verified`, непроверенные предложения пройдут. Клиентская проверка поля `verification` закрыла бы это, но в задание не входила.
4. **Строка лога без ограничения длины.** Текст статуса от Vast теперь печатается целиком, после маскирования. При очень длинном тексте строка будет длинной.
5. **Устаревшие места в SPEC (не менялись по указанию).** В пункте 8.2 о неудачном старте осталась фраза «обрезается до 200 символов». В таблице значений раздела 3 ключа `verified` нет. Оба места требуют отдельной правки. Строка журнала о них упоминает.
6. **Смысл значения `verified`** остаётся UNVERIFIED относительно веб-интерфейса Vast (раздел 4).
