# Отчёт: правило рабочего языка в SPEC и сверка `verified` в пробе Vast

Дата: 2026-10-13. Путь в репозитории: `probe_change_report.md` (корень).

Что сделано: правило рабочего языка добавлено в SPEC; проба `Generate/tools/vast_probe.py` делает второй сырой поиск с `verified=True` и печатает два числа. Живых вызовов Vast, GHCR, Gemini, Hugging Face и GitHub не было. Workflow не запускался. Коммит и push не делались. Production-код (`Generate/core/`, `cli.py`, оркестратор, воркер) не менялся.

Текст вложенного пункта:

> Рабочий язык исполнителя (с 2026-10-13): внутренние рассуждения, планы и заметки можно вести на английском. Всё, что видит пользователь или что попадает в репозиторий, остаётся на русском: ответ в чате, Markdown-отчёты, тексты логов и ошибок, текст SPEC, комментарии в коде. Существующие строки, идентификаторы и форматы логов не переводятся. Правило меняет только рабочий процесс, поведение кода не меняется.

Журнал изменений (раздел «v0.3», верх списка), две строки с датой 2026-10-13:

2. Проба `vast_probe.py`: второй поиск с `verified=True`, два числа, блок `search_verified_check`. Поле подтверждения хоста: UNVERIFIED. Статус: живой прогон не выполнялся.

Другие разделы SPEC не менялись. Номер версии (0.3) не менялся.

## 2. Что изменено в пробе (`Generate/tools/vast_probe.py`)

Файл по функциям:

- **Докстринг модуля**: список вызовов теперь содержит два поиска (без `verified` и с `verified=True`) и `search_offers`. В описании кодов выхода сказано, что сбой второго поиска даёт код 3, а результат первого поиска и блок `search_verified_check` всё равно записываются.
- **Импорт**: добавлен `dataclasses`.
- **Константы** (после `SNIPPET_LIMIT`): `VERIFY_KEY_MARKER = "verif"` и `VERIFY_FIELD_MISSING = "поля verified в предложениях нет"`. Над ними комментарий с пометкой UNVERIFIED.
- **Новая `_offers_of(raw)`**: список `offers` из ответа; при неожиданной форме пустой список.
- **Новая `_verify_field_names(offers)`**: имена ключей предложений, в которых есть подстрока `verif` (без учёта регистра). Имена с признаками секретов (`_is_sensitive`) пропускаются.
- **Новая `_check_verified(client, offer_filter, count_plain, show_count)`**: копирует фильтр через `dataclasses.replace(offer_filter, verified=True)`, строит запрос через `VastClient._build_query` и отправляет `client._request("POST", PATH_BUNDLES, ...)`. Печатает строки (раздел 3). Возвращает блок для JSON и признак сбоя.
- **`main()`**:
  - переменная `verified_check` до вывода;
  - вызов `_check_verified` сразу после печати первых предложений первого поиска (шаг «1б»), до шага production-правил;
  - `failed = failed or verified_failed`;
  - в `payload` добавлен ключ `search_verified_check`.

Не менялись: `_request`, `_build_query`, `search_offers`, `_sanitize`, вызовы счёта, путей и Hugging Face, существующие строки вывода. Если первый поиск падает, пробы по-прежнему сразу выходят с кодом 3 без записи файла.

Сетевые вызовы пробы после изменения: три POST на `/api/v0/bundles/` (без фильтра, с `verified=True`, `search_offers`), остальные вызовы без изменений.

## 3. Строки, которые проба печатает теперь

| Когда | Строка | Поток |
|---|---|---|
| Начало шага | `=== Поиск с фильтром verified=True (сверка числа предложений) ===` | stdout |
| Поиск выполнен | `Предложений без фильтра verified: N; с фильтром verified: M` | stdout |
| Поиск выполнен, предложений нет | `Предложений нет: поле подтверждения хоста не проверено.` | stdout |
| Есть ключи с подстрокой `verif` | `Поля предложения с подстрокой «verif» (UNVERIFIED): <имена>` | stdout |
| Есть ключи, первые предложения | `  #K: <имя>=<значение>; ...` (`нет поля`, если ключа в предложении нет) | stdout |
| Ключей нет | `поля verified в предложениях нет` | stdout |
| Сбой второго поиска | `Сбой поиска предложений Vast с фильтром verified: <текст ошибки>` | stderr |
| Сбой второго поиска | `Предложений без фильтра verified: N; с фильтром verified: не получено (ошибка поиска)` | stdout |

Пример на мок-значениях. Это локальная проверка на мок-ответе, не результат запуска против Vast. Имя `host_verified` выдумано для мока и не подтверждено для Vast.

Вариант 1: поле найдено.

```
=== Поиск с фильтром verified=True (сверка числа предложений) ===
Предложений без фильтра verified: 5; с фильтром verified: 3
Поля предложения с подстрокой «verif» (UNVERIFIED): host_verified
  #1: host_verified=True
  #2: host_verified=True
  #3: host_verified=True
```

Вариант 2: поля нет.

```
Предложений без фильтра verified: 5; с фильтром verified: 3
поля verified в предложениях нет
```

Вариант 3: второй поиск упал (код выхода 3; первый результат и `probe_result.json` сохраняются).

```
stderr: Сбой поиска предложений Vast с фильтром verified: Vast API вернул HTTP 500: POST /api/v0/bundles/. Ответ: boom ***
stdout: Предложений без фильтра verified: 5; с фильтром verified: не получено (ошибка поиска)
```

Новый блок в `probe_result.json` (тот же пример):

```json
"search_verified_check": {
  "count_without_verified": 5,
  "count_with_verified": 3,
  "field_names": ["host_verified"],
  "error": null
}
```

Ключи блока (`count_without_verified`, `count_with_verified`, `field_names`, `error`) не содержат признаков секретов, поэтому `_sanitize` их не удаляет. Значения полей в JSON не пишутся, только имена.

Строка про отсутствие поля: в задании её текст дан дважды, в правиле 6 короче («поля нет»), в части B полностью («поля verified в предложениях нет»). Выбран полный текст из части B.

Существующие строки вывода не менялись.

## 4. Поля, которые не подтверждены (UNVERIFIED), и где они отмечены

1. **Поле подтверждения хоста в предложении Vast.** Имя и значения в репозитории не подтверждены. Имя не угадывается: проба печатает ключи предложения, в которых есть подстрока `verif`, и их значения у первых предложений. Отмечено в трёх местах:
   - комментарий над `VERIFY_KEY_MARKER` в `vast_probe.py`;
   - комментарий и строка вывода `(UNVERIFIED)` в `_check_verified` / `_verify_field_names`;
   - `Generate/SPEC.md`, журнал изменений, строка от 2026-10-13 про пробу.
2. **Ключ `verified` в запросе** (`{"eq": True}`). Он взят из существующего `VastClient._build_query` (production-код, не менялся). Живой ответ Vast на этот ключ в репозитории не проверен. Отмечено комментарием над константами в `vast_probe.py`.

## 6. Риски

1. **Ключ `verified` может не совпадать с реальным полем Vast.** Если сервер его не понимает, счёт с фильтром совпадёт со счётом без фильтра. Это не доказывает, что фильтр не работает, и ошибки при этом не будет.
2. **Поиск по подстроке `verif` может не попасть в нужное поле.** Может найтись служебное поле с похожим именем, а настоящее поле, названное иначе, — не найтись. Пустой вывод не означает, что хост не подтверждён.
3. **Счёт — это снимок.** `_build_query` задаёт `limit: 100`, поэтому каждое число не больше 100 на запрос. Рынок меняется между запросами, и разница между N и M может быть шумом.
4. **Новый путь к коду 3.** Если падает второй поиск, проба выходит с кодом 3, и workflow станет красным, хотя первый поиск прошёл. Так велит докстринг, но для оператора это новая ситуация.
5. **Нагрузка.** Проба делает три POST на `/api/v0/bundles/` вместо двух. Для лимитов Vast это мало, но учитывать стоит.
6. **Production не меняется.** `search_offers` по-прежнему без `verified`. Если фильтр понадобится в production, это отдельное решение.
7. **Что не проверено.** Живых вызовов не было. Pypi недоступен из среды, поэтому httpx и существующие pytest-тесты здесь не запускались. Пример строк выше получен на мок-ответе с заглушкой HTTP-клиента. Полный прогон тестов и ручной запуск `vast-probe` делает пользователь на GitHub.
