# SPEC.md: паспорт проекта videogen (Generate)

Версия 0.2 (правка 4 октября 2026: режим `trial` убран, добавлены правила тестов 0.3 и лимиты Gemini). Архитектура: GitHub Actions + Vast.ai + ComfyUI (headless). Это единый источник договорённостей для всех модулей. Каждый чат читает только свой раздел (grep по заголовку `## N.` или чтение диапазона), не файл целиком.

Версия 0.1 (локальное приложение: FastAPI + SQLite + start.bat) заменена. Её каркас остаётся в репозитории как «устаревший каркас локального приложения» (см. раздел 2). Соответствие старых и новых разделов: таблица в конце файла.

## 0. Правила для всех чатов

1. Не читать большие файлы целиком: grep по нужным строкам или чтение диапазона. Для первой части (Download/) целиком не читать `generate_queries.py`, `search.py`, `download.py`, `result.srt`.
2. Не менять чужие модули. Если нужен новый метод у чужого модуля, написать об этом в отчёте. Первая часть (`Download/`, `download.yml`) не трогается никогда.
3. Каждый модуль имеет короткий `README.md` рядом: входы, выходы, ошибки.
4. Ошибки не глотать молча. Статус клипа меняется на `done` только после реально проверенного успеха (клип лежит в Release, размер совпадает).
5. Все тексты логов и сообщений на русском. Промпты для видеомодели на английском.
6. Модель, версии и параметры не зашивать в код: только через профиль модели (раздел 5).
7. Пути входных файлов (`final.srt`, `missing.txt`) не зашивать в код: только параметры командной строки. Значения по умолчанию (`final.srt`, `missing.txt` в корне репозитория) живут во входах workflow, не в Python.
8. Воркер (исполнитель задачи) в конце работы сразу присылает в чат все изменённые и созданные файлы по отдельности, с путями от корня репозитория.

### 0.1. Правила работы с ключами (обязательны для каждого модуля)

Секреты: `GEN_GEMINI_API_KEY`, `GEN_VAST_API_KEY` (отдельные от ключей первой части). В Actions они приходят из Secrets репозитория, локально из переменных окружения. Токен `GITHUB_TOKEN` (для `gh`) подчиняется тем же правилам.

1. Ключи читаются только из переменных окружения. В коде, yaml, конфиге, профиле, README, тестовых данных их нет.
2. Ключ нигде не печатается: ни в логи, ни в f-строки, ни в тексты исключений, ни в имена файлов, ни в артефакты, ни в `prompts.json`, ни в описание Release. Ни целиком, ни частью (маска вида `sk-...abcd` тоже запрещена: даже хвост не печатаем).
3. Ключ не передаётся в аргументах командной строки (виден в списке процессов): только через окружение процесса или заголовок запроса.
4. Запросы к API: ключ в заголовке (`x-goog-api-key` для Gemini, `Authorization: Bearer` для Vast), не в URL. Иначе он попадёт в traceback и в логи библиотек. Точные имена заголовков сверить с документацией на этапах 4 и 6.
5. Исключения сетевых клиентов перед выводом очищаются: сообщение строится вручную из безопасных полей (статус, код ошибки), объект запроса и заголовки в текст не попадают. Логирование уровня DEBUG у HTTP-библиотек отключено.
6. Производные токены (например токен воркера на карте) маскируются сразу после создания: ядро вызывает `reporter.mask(value)`; в Actions-адаптере это печать `::add-mask::<значение>`, в локальном адаптере регистрация значения в фильтре логов. Маскирование идёт до первого использования значения.
7. Запрещены дампы окружения: `env`, `printenv`, `set -x` вокруг секретов, `os.environ` целиком в логах и отчётах об ошибках.
8. Токен воркера на карту передаётся через окружение контейнера, не через аргументы запуска. Основной `GEN_VAST_API_KEY` на карту не передаётся (способ самоуничтожения карты: раздел 8, слой (а)).
9. Workflow запускается только вручную (`workflow_dispatch`). `pull_request`, `pull_request_target`, запуск из форков не используются. Репозиторий публичный: всё, что попало в лог, артефакт или Release, видит весь интернет.
10. Каждый модуль, обращающийся к ключам, покрывается тестом: подставляется заведомо узнаваемое значение ключа (например `TESTKEY-12345`), вызывается нормальный путь и путь с ошибкой, проверяется, что значения нет ни в захваченных логах, ни в тексте исключения, ни в созданных файлах.

### 0.2. Переносимость на локальное приложение

Локальная версия возможна позже, поэтому ядро переносимо. Четыре принципа:

1. Ядро (`Generate/core/`) это обычные Python-модули. Запускаются командой с аргументами (`python -m Generate.cli ...`). Yaml только вызывает эту команду и ничего не решает.
2. Ключи только из окружения (0.1).
3. В ядре нет обращений к `GITHUB_*`, артефактам, Releases, `$GITHUB_STEP_SUMMARY`. Всё это делает отдельный «выходной адаптер» (раздел 9) через два узких интерфейса: `ReleaseStore` (список файлов, залить, скачать, создать хранилище) и `Reporter` (лог, группа, итог, маска). Локальное приложение подставит свои реализации (папка на диске, консоль/страница).
4. Состояние только в файлах и умение продолжить после обрыва (раздел 4).

### 0.3. Правила тестов (что на заглушках, что вживую)

Принцип: платная только аренда Vast. Всё остальное бесплатно, поэтому заглушки нужны только там, где реальную проверку нельзя провести в среде, где пишется и гоняется код.

1. **Обычный `pytest`** (в рабочих чатах и у пользователя) работает на заглушках и не ходит в сеть. В рабочих чатах нет доступа к сети и ключам, поэтому там по-другому нельзя. Тесты не зависят от наличия ключей.
2. **Живые проверки бесплатных сервисов выполняются в Actions**, автоматически, до любых трат на Vast, в составе `generate.yml` (отдельный предварительный шаг) и никаких меток вроде `gemini_live` не требуют:
   - Gemini: ответ в нужном формате (раздел 7), работа цепочки моделей, отсутствие утечки ключа. Запросов немного: суточный лимит общий (раздел 7). Переключение на запасную модель при исчерпании квоты живьём не проверяется (для этого пришлось бы сжечь сотни запросов), только на заглушке, которая имитирует ответ «квота исчерпана».
   - GitHub Release: создание, три проверки при старте, заливка, `--clobber`, `generated_links.txt`. Токен встроенный (`GITHUB_TOKEN`), ключей не нужно. Проверки можно вести на отдельном служебном теге, который потом удаляется.
3. **Платное (Vast, настоящая карта, ComfyUI, воркер с моделью)** живьём проверяется только на пробном прогоне (раздел 8.3(д), этап 10), и только после того, как весь код принят и сценарий целиком (обрыв, докачка, потолок бюджета, уничтожение карт, лимиты) прогнан на заглушках.

## 1. Общая схема

```
Раннер GitHub Actions (один job)                     Карты Vast.ai (1..max_cards)
┌────────────────────────────────────┐               ┌─────────────────────────────┐
│ cli.py -> оркестратор               │               │ worker/server.py (HTTP)     │
│  ├ missing.txt + final.srt          │               │  принять задачу             │
│  ├ Gemini: промпты (порт, раздел 7) │ ──POST /task─>│  граф -> ComfyUI headless   │
│  ├ клиент Vast: аренда/уборка       │ <─GET /task───│   (локальный API карты)     │
│  └ выходной адаптер -> Release      │ <─GET /file───│  отдать файл (Range)        │
│                                    │               │                             │
│ клип получен -> залит в Release ->  │ ──POST /ack──>│  удалить файл у себя        │
│ удалён с раннера                    │               │  dead-man switch (раздел 8) │
└────────────────────────────────────┘               └─────────────────────────────┘
          │
          └─> GitHub Release gen-<хэш>: клипы, prompts.json, generated_links.txt
```

- Инициатор всегда раннер: он подключается к воркеру (опрос раз в 1-2 с, скачивание по запросу). Воркер никуда сам не ходит, кроме самоуничтожения (раздел 8, слой (а)). Доступность портов карты с раннера: открытый вопрос 13.
- Воркер запускает ComfyUI headless и обращается к нему по локальному API. Контракт воркера (раздел 8) от этого не зависит.
- Воркер ничего не знает о проекте: получает `num`, `prompt`, `num_frames`, `seed`, возвращает файл.
- Очередь общая, в памяти оркестратора: воркер получает следующий клип, когда свободен. Статического деления нет.
- Клип на раннере живёт ровно столько, сколько идёт загрузка в Release: сразу после успешной загрузки удаляется, и только после этого карте уходит `ack`.
- Рабочий процесс пользователя: часть 1 (`Download/`) даёт `final.srt` и после ручной чистки `missing.txt`; оба файла кладутся в корень репозитория рядом с `result.srt`; пользователь запускает `generate.yml` вручную.

Одноимённые заготовки в `app/services/` (naming, vast_client, budget, orchestrator, gemini_prompts) основой не считать: каждый модуль заново пишется в `Generate/core/` своим этапом (раздел 12).

## 4. Состояние (вместо БД)

БД и SQLite нет. Состояние это файлы и умение продолжить после обрыва.

- **Источник правды по готовым клипам: сам Release** (список его файлов, включая релизы `-partN`). При старте и после обрыва оркестратор получает список файлов Release и пропускает номера, у которых клип уже лежит. Файл в Release = `done`, независимо от того, что записано в `prompts.json`.
- **`prompts.json`** с промптами и статусами хранится как файл в том же (основном) Release. Это файловый чекпоинт Gemini: повторный запуск не тратит квоту заново. Содержимое: хэш `final.srt` (как в разделе 9), имя модели и профиль, затем по каждому номеру: `num`, `start_ms`, `end_ms`, `clip_ms`, `num_frames`, `prompt`, `status`, `attempts`, `error`, `needs_review`. Ключей и токенов в нём нет (0.1). Запись атомарная: временный файл, затем замена; заливка в Release `--clobber` после каждого батча Gemini и затем не чаще, чем раз в N готовых клипов (N уточнить на этапе 8).
- **Статусы клипа:** `new` (промпта нет), `ready` (промпт есть), `queued`, `running`, `downloading` (клип забирается с карты и заливается в Release), `done`, `failed`. Хранятся в памяти оркестратора и в `prompts.json`.
- **Переходы:** `ready -> queued -> running -> downloading -> done`. При потере карты `running|downloading -> queued`, `attempts += 1`. Больше 3 попыток -> `failed`.
- **Правила продолжения (решение A2):** при старте клип, найденный в Release, получает `done`; статусы `queued|running|downloading` сбрасываются в `ready`; `failed` тоже возвращается в `ready` с `attempts = 0` (повторный запуск это осознанное решение пользователя), причина прошлого провала пишется в лог.
- Мелкое состояние запуска (слоты, поколения карт, расход) живёт в памяти и в итоговом отчёте; между запусками не переносится. Расход ограничен на каждый запуск отдельно (раздел 8).
- `num`: номер сегмента из SRT, он же номер файла. Не меняется никогда.

## 5. Профиль модели (`Generate/model_profiles/<имя>.yaml`)

Всё, что зависит от конкретной модели, живёт только здесь. Пути внутри профиля относительные от папки `Generate/`.

```yaml
name: ltx25
frame_rule: {kind: "8k+1", min_frames: 9}   # допустимые num_frames; проверить по документации модели
max_sec_hint: 10          # для предупреждения, уточнить на тестах
image: ...                # docker-образ
weights: [...]            # что качать, источники, размеры
workflow:
  file: model_profiles/workflows/ltx25.json   # граф ComfyUI (API-формат)
  bindings:               # параметр -> (node_id, поле) для подстановки значения в граф
    prompt: {node_id: "...", field: "..."}
    num_frames: {node_id: "...", field: "..."}
    seed: {node_id: "...", field: "..."}
    filename_prefix: {node_id: "...", field: "..."}
  output: {node_id: "...", type: video}       # нода, отдающая результат, и тип: video|image
inputs: []                # необязательно: необязательные входы модели, например референсы
                          # элемент: {name, kind: image|video|text, node_id, field, optional}
params: {cfg: 1.0, resolution: "1152x640", quantization: "fp8-cast"}
vram_gb_expected: ...
prompt_style: model_profiles/prompt_styles/ltx25.md   # инструкция для Gemini
response_format: {...}    # структура ответа Gemini под эту модель (раздел 7)
```

Тип результата (видео или фото) и всё модельно-зависимое (граф, подстановки, необязательные входы, файл стиля) описывается только профилем. Значения `inputs` (референсы) лежат файлами в репозитории и задаются профилем; файлы едут на карту вместе с заданием. Так как репозиторий публичный, референсы тоже публичны. Что точно поддерживает граф, выяснится на тестах (раздел 13).

Чтобы поддержать другую модель, добавляется новый yaml и новый файл стиля, код не меняется. Значения, помеченные «проверить», нельзя считать проверенными до первого пробного прогона.

## 6. Расчёт длины клипа (`core/timing.py`)

Вход: список сегментов SRT с `start`, `end` в мс (отсортирован по номеру).

**Тайминги считаются по ПОЛНОМУ `final.srt`** (длина клипа зависит от начала следующего сегмента, даже если следующий в `missing.txt` не входит). Результат затем фильтруется по номерам из `missing.txt`: считается всё, в работу берутся только они.

1. `raw_i = start_{i+1} - start_i`. Это длительность сегмента плюс пауза до следующего. Для последнего: `raw_last = (end - start) + tail_pad_sec`.
2. Если `raw_i < clip_min_sec` -> оставить как есть, записать предупреждение «короче минимума» (SRT нормализуется отдельно, в первой части).
3. Если `raw_i > clip_max_sec` -> предупреждение в лог и в итог. Если `raw_i > gpu_max_sec` -> отдельное сообщение «выше максимума, который тянет карта». Клип всё равно ставится в очередь; решение по нарезке откладывается до реальных прогонов.
4. `frames_i = ceil(raw_i * fps)`, затем округление ВВЕРХ до ближайшего допустимого значения по `frame_rule` профиля. Пример для 8k+1 при 24 fps: 4.0 с -> 96 -> 97 кадров.
5. `clip_ms_i = frames_i / fps * 1000` (для информации).

Принцип: клип минимально возможной длины, не короче нужной. Лишний хвост до доли секунды допустим, обрезка остаётся на этапе монтажа (воркер может обрезать через ffmpeg, если включено; открытый вопрос).
Пауза между сегментами уже входит в `raw_i`, отдельно её не добавлять.
Модуль: чистая функция, без сети. Юнит-тесты (уже есть, переносятся): обычный сегмент, большая пауза, нулевая пауза, последний сегмент, границы округления, смена `frame_rule`. Добавляется тест: фильтр по `missing` не меняет значения для оставшихся номеров.

## 7. Gemini: SRT -> промпты (`Generate/core/gemini_prompts.py`)

Новый модуль это **порт** в `Generate/core`, а не копия. `Download/generate_queries.py` не трогается и не копируется как есть; его идеи переиспользуются:

- парсинг SRT с проверкой пропусков/дублей и хэшем файла (`srt_parser`);
- склейка сегментов в предложения (`Sentence ... >>сегмент<< ...`, `Before`, `After` по целым предложениям);
- батчи по `gemini_batch_size`, structured output (JSON-массив, `segment_index` в каждом объекте), проверка, что вернулись ровно нужные номера;
- ретраи с бэкоффом, различение дневной квоты и RPM, цепочка запасных моделей (`gemini_models`), preflight, чекпоинт с проверкой хэша SRT, атомарная запись.

Не переносить: режимы источников, запрещённые типы кадра, годы, `entity_keywords`, три запроса, `visual_value`, двухкруговой REPAIR.

Особенности второй части:

- **Вход: только номера из `missing.txt`.** Промпты пишутся только для них. Номер, которого нет в `final.srt`, ошибка до первого обращения к Gemini.
- **Контекст предложений строится по ПОЛНОМУ SRT.** Склейка в предложения, `Before`, `After` считаются по всем сегментам, затем выбираются записи для нужных номеров.
- **Запуск из раннера.** Ключ `GEN_GEMINI_API_KEY` из окружения, в заголовке (0.1). Доступ к Gemini с раннера GitHub это причина переезда.
- **Чекпоинт теперь файл:** `prompts.json` (раздел 4), лежит в Release. При старте скачивается, проверяется хэш SRT и модель/стиль; для номеров, у которых промпт уже есть, Gemini не вызывается. Если хэш не совпал, остановка с понятным текстом (до всяких трат).

Контракт ответа (по умолчанию, может расширяться профилем): `[{"segment_index": int, "prompt": str}]`. Номер никогда не передаётся внутри текста. Формат «12: промпт» только для показа и экспорта.

Промпт под модель: системная инструкция собирается из файла `prompt_styles/<модель>.md` (профиль) + `style_brief` + контекст сегмента. Содержимое файла стиля опирается на официальную документацию по промптингу выбранной модели (структура описания, порядок элементов, длина, камера и движение, что запрещено). Для другой модели создаётся другой файл, `response_format` может отличаться.

Лёгкая валидация после ответа: непустой prompt, длина в пределах профиля, нет служебного мусора, один retry батча при нарушении; остаток получает флаг `needs_review` (не статус). Интерфейса проверки нет, поэтому такие промпты всё равно идут в генерацию, а их список выводится в итог запуска (решение A2; проверять промпты помогает пробный прогон).
Прогон идемпотентный: уже готовые промпты не перезаписываются. Что уходит на карту: только поле `prompt` (плюс `inputs` профиля).
**Лимиты Gemini (данные пользователя, не проверены автором SPEC; сверить с документацией Google на этапе 4).** Для каждой из двух моделей цепочки: 15 запросов в минуту (RPM), 250 000 токенов в минуту (TPM), 500 запросов в сутки (RPD). Суммарно по двум моделям лимит 1000 запросов в сутки (RPD складывается). RPM и TPM не складываются: в каждый момент работает только одна модель, запасная включается лишь когда у основной исчерпана суточная квота (RPD), поэтому ограничение по минуте всегда считается для одной активной модели, то есть 15 RPM и 250k TPM. Следствия для модуля:
- ограничитель скорости держит запросы в пределах `gemini_rpm_limit` и `gemini_tpm_limit` (размер батча и пауза считаются из них);
- счётчик суточных запросов ведётся отдельно по каждой модели; при достижении `gemini_rpd_limit` (или ответе «дневная квота») модуль переходит к следующей модели цепочки; когда исчерпаны обе, остановка с понятным текстом без траты денег;
- ответ «превышен RPM» это не дневная квота: ждать и повторять, на запасную модель не переходить.

Модуль тестируется на заглушке Gemini (без сети, включая сценарий «квота исчерпана») и тестом на утечку ключа (0.1, п.10); живая проверка формата ответа и цепочки выполняется в Actions по правилу 0.3.

## 8. Оркестратор и воркер

### 8.1. Контракт воркера

HTTP, токен в заголовке (`X-Worker-Token`). Токен генерируется на запуск, сразу маскируется (0.1, п.6) и передаётся на карту через окружение контейнера.

- `POST /task` `{num, prompt, num_frames, seed}` -> `{task_id}`
- `GET /task/{id}` -> `{state: queued|running|done|error, stage, log_tail, size_bytes?, error?}`
- `GET /file/{id}` -> файл (поддержка Range для докачки)
- `GET /health` -> `{ok, gpu, vram_free, busy}`
- `POST /ack/{id}` -> воркер удаляет файл только после подтверждения от раннера.

Внутри воркер собирает граф из `workflow.file`, подставляя значения по `bindings`, отправляет в локальный ComfyUI и ждёт результат. Необязательные `inputs` передаются дополнительным полем `inputs` (формат уточнит этап 7). Любой запрос с верным токеном считается heartbeat.
Воркер держит не более 2-3 нескачанных клипов и не берёт новую задачу, пока очередь на скачивание не разгребётся.

### 8.2. Оркестратор

- Оркестратор это CLI-процесс внутри job раннера (не сервис). Запуск: `cli.py` с параметрами раздела 3.
- Общая очередь из клипов со статусом `ready|queued` (после раздела 6 и 7); воркеры получают следующий клип, когда свободны.
- Слот N = линия работы; потеря карты (preempt/timeout/потолок жизни) -> новое поколение N.(g+1) в том же слоте; клипы, не подтверждённые как `done`, возвращаются в очередь. Обозначение карты: «слот.поколение» (карта 1.2).
- Карта не удаляется, пока все её клипы не `done` (или не возвращены в очередь).
- **Путь клипа:** `GET /file` (Range, проверка размера) -> заливка в Release по одному (раздел 9) -> удаление файла с раннера -> `POST /ack`. `ack` только после успешной заливки; при сбое заливки клип остаётся на карте и забирается повторно.
- **Лимит job GitHub 6 часов.** Перед началом оценивается, укладывается ли работа: `нужно_карт = ceil(клипов * среднее_время_клипа / (job_deadline_min - запас_на_старт))`. Стартует с малого числа карт; по первым замерам число карт увеличивается (не выше `max_cards` и пока позволяет бюджет). Если и так не укладывается, при достижении `job_deadline_min` новые клипы не берутся, готовое дозаливается, итог «частично». При обрыве или частичном итоге повторный запуск с тем же релизом (раздел 9) продолжает с оставшихся номеров. Что происходит при превышении 6 часов на практике: проверить (раздел 13).
- **Число карт подстраивается без лимитера скорости** (сеть раннера не узкое место); ограничивают время, `max_cards` и бюджет.
- **Память и диск:** на карте не более 2-3 нескачанных клипов; на раннере клип удаляется сразу после загрузки в Release; одновременно на раннере лежит не больше нескольких клипов (размер диска раннера: открытый вопрос).
- `concurrency` в `generate.yml` не даёт запустить два прогона одновременно (`cancel-in-progress: false`): два прогона по одному релизу = двойные траты и гонка за файлы.
- Коды завершения CLI (итоговые значения закрепить на этапе 8): 0 всё готово или генерировать нечего; 2 ошибка входов/проверок (ничего не потрачено); 3 частично (бюджет, время или `failed`).

### 8.3. Защита денег (все слои обязательны)

Все карты запуска помечаются меткой `gen-<GITHUB_RUN_ID>` (имя метки передаёт адаптер; ядру нужна только строка-метка).

- **(а) Dead-man switch на карте.** Если от раннера нет ни одной команды или heartbeat `worker_idle_timeout_min` минут, карта сама себя уничтожает через API Vast (или завершает работу, если уничтожение невозможно). Основной `GEN_VAST_API_KEY` на карту не передаётся (0.1, п.8). Какой ограниченный ключ/механизм у Vast есть для самоуничтожения изнутри инстанса: уточнить на этапах 6-7, добавлено в раздел 13.
- **(б) Жёсткий потолок жизни карты** `card_max_lifetime_min` независимо от heartbeat. Контролируется на карте (локальные часы воркера) и оркестратором (поколение завершается, при необходимости заводится следующее).
- **(в) Шаг `if: always()` в конце `generate.yml`**, который убивает все карты этого запуска (по метке). Выполняется и при падении, и при отмене запуска. Не зависит от оркестратора, использует отдельную короткую команду CLI.
- **(г) Плановый `cleanup_vast.yml`** (cron, частота уточнить): находит в аккаунте Vast инстансы с меткой `gen-*`, чей запуск уже завершён (проверка статуса запуска через API GitHub) или чей возраст больше `card_max_lifetime_min`, и убивает их. Право `actions: read`, `contents` не нужен.
- **(д) Бюджет и режимы:** потолок `budget_limit_usd` на запуск (расчёт по цене и времени аренды, сверка с реальным списком инстансов), `silent_host_timeout_min`, бан плохого хоста на запуск, **пробный прогон** это обычный запуск, а не отдельный режим: `max_cards` = 1, `limit_clips` = 3 (первые три номера из `missing.txt`), `budget_limit_usd` в несколько долларов. Клипы идут в тот же основной Release (без отдельного тега). Промпты пишутся только для этих номеров. Клипы пробы считаются готовыми, и полный запуск их пропускает. Если проба плохая, пользователь вручную удаляет файлы клипов из Release (и при необходимости их записи из `prompts.json`), и они генерируются заново.

Слои независимы: отказ одного (например падение оркестратора) закрывается следующим.

### 8.4. Логи воркера

Воркер логирует каждый этап с отметками времени (загрузка весов, энкодинг, сэмплинг, декод, апскейл, кроп, пережатие, пик VRAM): это основа анализа пробного прогона. Секреты в эти логи не попадают (0.1).

## 9. Выходной адаптер: GitHub Release (`core/release_adapter.py`)

Единственное место, где живут `gh`, `GITHUB_*`, `GH_TOKEN` (из окружения, правила 0.1). Ядро видит только интерфейсы `ReleaseStore` и `Reporter` (0.2, п.3).

### 9.1. Тег, название, описание

- Хэш: sha256 по правилу `srt_hash` из `srt_parser` (поле `num|start|end|text` по сегментам), считается по финальному `final.srt`.
- **Тег:** `gen-<первые 12 символов хэша>`. Тег = ключ поиска (`gh release view` / список релизов).
- **Название:** `gen-<12 символов> · YYYY-MM-DD HH:MM UTC`.
- **Описание:** полный sha256 и имя модели. Описание = проверка.
- Пробный прогон отдельного тега не имеет: он идёт в тот же релиз (раздел 8.3(д)).

### 9.2. Три проверки при старте

Все ведут к остановке без единой заливки и с понятным русским текстом:

1. По тегу найдено больше одного релиза (учитывая черновики): остановка, текст «найдено N релизов с тегом ..., удалите лишние вручную».
2. Релиз один, но полного хэша в описании нет или он не совпадает: остановка, текст «тег совпал, содержимое нет: возможен другой final.srt».
3. Хэш совпал: продолжить, пропустив номера, уже лежащие в релизе. Релиза нет: создать с хэшем и именем модели в описании.

Вход `release_tag` (необязательный): указывает тег вручную; проверки 1-3 действуют так же, а при отсутствии релиза он создаётся именно с этим тегом.

### 9.3. Заливка

- По одному клипу сразу после получения (раздел 8), `--clobber`; после успешной заливки локальный файл удаляется.
- Имя файла клипа **по образцу первой части**: `{номер}.{расширение}` (в `Download/download.py`: `filename = f"{number}.{fmt}"`, номер без нулей: `7.mp4`, `128.mp4`). Для клипа расширение `mp4`. Ширина номера берётся из `clip_name_width` (0 = без нулей, как в первой части; >0 = добавление нулей слева). Шаблон `filename_template` = `{num}.mp4`. Имя формирует `core/naming.py`.
- Заливка клипов, `prompts.json` и `generated_links.txt` идёт в один и тот же Release (основной).

### 9.4. `generated_links.txt`

В конце запуска: прямые ссылки по одной на строку, формат ровно как `release_links.txt` в `download.yml` (для Free Download Manager):
`https://github.com/<repo>/releases/download/<ТЕГ>/<имя файла>`. Строится по реальному списку файлов Release (а не по памяти), поэтому при повторном запуске включает и ранее залитые клипы. Служебные файлы (`prompts.json`, `generated_links.txt`) в список не входят. Файл заливается в тот же основной Release.

### 9.5. Лимиты GitHub и `-partN`

Лимиты GitHub: 1000 файлов на релиз, 2 GiB на файл. Если файлов станет больше `release_asset_limit` (по умолчанию 900, запас на служебные файлы), следующие клипы идут в релиз с тегом `<тег>-part2`, затем `-part3` и т.д. (название `... · часть N`, описание то же, с хэшем). Ссылки из всех частей собираются в один `generated_links.txt` в основном релизе. `prompts.json` лежит только в основном релизе. При старте проверки 1-3 применяются к каждой найденной части.

### 9.6. Формат `missing.txt` (по результату разбора первой части)

В `search.py` файл пишется так: номера сегментов, **по одному в строке, по возрастанию**, без пробелов и нулей слева (`f"{idx}\n"`). Шаг `Merge failed downloads into missing.txt` в `download.yml` дополняет файл номерами из `download_failed.txt`, сортирует (`sort -n -u`) и убирает дубли. **Если пропусков нет**, в файл пишется строка-заглушка: «Пропущенных сегментов нет - все найдены и успешно скачаны.» (иначе пустой файл ломает заливку в Release). Пользователь после этого вручную правит файл.

Правила разбора (`core/missing.py`):

- BOM и CRLF (правка на Windows) допускаются; пустые строки и пробелы по краям игнорируются; дубли сливаются с предупреждением.
- Строка из одних цифр = номер.
- Файл, где нет ни одного номера, и единственная непустая строка равна заглушке (сравнение без учёта регистра и пробелов по краям): **генерировать нечего, завершить успешно (код 0)**, в Summary написать «пропущенных нет», ни Gemini, ни Vast не вызывать, Release не создавать.
- Любая другая нецифровая строка, смесь номеров с заглушкой, пустой файл (0 номеров и нет заглушки) или номер, которого нет в `final.srt`: ошибка (код 2) до любых трат, с указанием строки.

## 10. Логи

- Логи раннера: в Actions, сгруппированы `::group::` (на каждый этап и карту), печатает `Reporter` Actions-адаптера. Событие: `{ts, slot, generation, level, line}`.
- Краткий итог запуска в `$GITHUB_STEP_SUMMARY`: сколько номеров в работе, сколько готово, сколько пропущено (`done` уже в Release), `failed` с причиной, `needs_review`, расход, ссылки на Release и на `generated_links.txt`, предупреждения по длине клипов (раздел 6), результат проверок раздела 9.
- Подробные логи карт: маленькие текстовые артефакты (`card_<слот>.<поколение>.log`), не видео, срок хранения короткий (уточнить, порядок 7 суток). Выгружаются шагом `if: always()`.
- Маскирование ключей обязательно (0.1). Публичный репозиторий: считать, что любая строка лога видна всем.
- Воркер на карте не логирует тело запросов с токеном.

## 11. Интерфейс

Страницы заменены на **входы workflow + итог в Summary**:

1. Входы `generate.yml` (раздел 3) = бывшая страница настроек/проекта.
2. Итог в `$GITHUB_STEP_SUMMARY` + логи Actions (раздел 10) = бывшие таблица промптов и мониторинг.
3. Release = результат и `generated_links.txt` для менеджера загрузок.

Старые страницы (настройки, проект, таблица промптов, мониторинг, SSE-панели логов) помечены **устаревшими**; шаблоны остаются в «устаревшем каркасе» (раздел 2). Локальное микро-приложение для правки `missing.txt` у пользователя вне рамок этого SPEC.

## 13. Открытые вопросы (решаются по ходу)

Действующие:

- Допустимые значения `num_frames` для выбранной версии модели: подтвердить по документации (в профиле «8k+1», не проверено).
- Что делать с клипами длиннее `gpu_max_sec`: решение после реальных прогонов, пока только предупреждение.
- Нужен ли ffmpeg-обрез хвоста на воркере или достаточно монтажа.
- Приватность на маркетплейсе Vast: нужен ли фильтр только верифицированных датацентров.
- Облачная выгрузка (R2) как страховка: не входит; роль хранилища выполняет Release.
- Как подавать референс стиля внутри модели (text-to-video через ветку графа): какой механизм поддерживает версия модели, стоимость по VRAM и скорости. Не подтверждено, решается по тестам, затем оформляется блоком `inputs` профиля.
- Отключение генерации звука в графе: звук в промптах не описывается; выяснить, можно ли отключить генерацию звука (экономия GPU).
- Версия ComfyUI и набор нод, закреплённые в образе (воспроизводимость графа).

Новые:

- **Доступность портов карты Vast с раннера GitHub** (прямое подключение по IP и порту): подтвердить на этапе 6-7; если порт не пробрасывается, нужен другой способ связи (уточнить, не придумывать).
- **Шифрование канала раннер-карта**: HTTP по публичному IP передаёт токен воркера открыто; выяснить, даёт ли Vast TLS/прокси, оценить риск.
- **Самоуничтожение карты изнутри**: какой ограниченный ключ или механизм у Vast есть (этапы 6-7); пока основной ключ на карту не передаётся.
- **Точные API-ID моделей Gemini** (основная 3.5 Flash Lite, запасная 3.1 Flash Lite): проверить по документации Google на этапе 4.
- **Поведение при превышении 6 часов**: что именно делает GitHub с job и успеет ли отработать шаг `if: always()`; проверить.
- **Размер диска раннера** и безопасное число одновременно лежащих клипов.
- **Лимиты `gh release upload`** (частота, повторные попытки) при заливке сотен файлов по одному.
- **Плановые workflow в публичном репозитории**: GitHub отключает `schedule` после периода неактивности репозитория; проверить условия для `cleanup_vast.yml` (раздел 8, слой (г)) и частоту cron.
- **Публичность результатов**: клипы, `prompts.json`, референсы и логи в публичном репозитории видны всем; принято пользователем, но фиксируется как риск.
- **Значения по умолчанию, предложенные в A2**: `card_max_lifetime_min` = 90, `job_deadline_min` = 330, `clip_name_width` = 0; подтвердить на пробном прогоне.
- **Частота обновления `prompts.json` в Release** (раздел 4) и срок хранения артефактов логов.
